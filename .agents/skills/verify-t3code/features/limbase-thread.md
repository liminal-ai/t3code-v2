# A Claude thread on Limbase

A Claude instance with a Limbase home runs its threads on Limbase. Each thread gets one Limbase thread, every message is captured there, and when the thread's context passes the compact trigger the session moves to a compacted view and goes on. The agent can read folded history back with `mcp__limbase__get_turns`. A step that Limbase fails shows Limbase's reason in the thread. Edit from here rolls the Limbase thread back to the kept turn. Fork is not native on a Limbase thread yet. A thread on any other instance runs as before.

## Sub-features

- `limbase-turn` runs a turn with tool calls on a Limbase instance, and Limbase holds its turns.
- `limbase-install` moves the session to a view in the middle of a turn, and the turn carries on with the thread's rules and tools.
- `limbase-retrieval` lets the agent call `mcp__limbase__get_turns` and `mcp__limbase__get_messages`.
- `limbase-restart` resumes the session Limbase last installed after a server restart.
- `limbase-service-restart` keeps a thread working after the Limbase service restarts, with the thread taken over by the restarted service.
- `limbase-edit` rolls the Limbase thread back on Edit from here, so the answer knows nothing after the kept turn, and the next turns and a restart go on from there.
- `limbase-edit-first` gives a thread whose first message is edited a new Limbase thread.
- `limbase-edit-failed` fails a step whose rollback Limbase did not make with the reason and the edit that gets past it.
- `limbase-fail-out` fails the run with a provider error `limbase: stopped at ...` when Limbase is down past its 90-second window, at a prompt or at a tool boundary, and the next turn works once Limbase is back.
- `limbase-fork` turns a fork into a fresh session with `Could not fork the source conversation natively (Limbase does not fork threads yet). ...`.
- `limbase-plain` leaves a thread on a plain Claude instance unchanged.

## How to get to it (user POV)

- Settings > Providers: a Claude instance's **Limbase home** and **Binary path**, per `docs/user/claude-limbase.md`.
- Pick that instance in the composer's model picker and send a message.

## Driving it with t3v

Preconditions:

- A Limbase lane of the run's own, never prod's, on the Limbase commit in `vendor/limbase/pin.json`: from a clean Limbase checkout at that commit with `pnpm install --frozen-lockfile` done, run `MEMBASE_CONVEX_PORT=<free even port, check ss -H -ltn> MEMBASE_DERIVATIONS='{"inference":{"fake":{"delayMs":0}}}' .agents/skills/verify-limbase/scripts/lane.sh up <dir>` then enroll its machine with `MEMBASE_HOME=<dir>/home pnpm exec limbase enroll --name lane` and `pnpm exec limbase machine approve --yes --admin-key-file <dir>/convex/admin.key '<the line enroll printed>'`, and wait for `lane.sh doctor <dir>` to end `limbase api 2 ... ok`. The lane runs its summaries on test inference, so it needs no model login. `<dir>` goes under the run's scratch folder, and the home is `<dir>/home`. `lane.sh start <dir>` starts its service again, and `lane.sh down <dir>` stops the lane.
- Every inference on this machine goes through the local gateway that `ANTHROPIC_BASE_URL` and `ANTHROPIC_AUTH_TOKEN` name in the shell the dev server starts from. Keep them, print neither, and never use the stored Claude login.
- `node $T3V doctor` prints no `FAIL`, and a disposable git project is added with `node apps/server/src/bin.ts project add --base-dir <worktree>/.t3 <folder>`.
- A Claude Code binary at the version in `vendor/limbase/limbase-host-agent-sdk-*.tgz` `package.json` `limbase.claudeCode`. `docs/user/claude-limbase.md` installs one.

- **Instance.** Run `node $T3V settings providerInstances='{"claudeLimbase":{"driver":"claudeAgent","displayName":"Claude Limbase","config":{"limbaseHome":"<dir>/home","binaryPath":"<claude binary>","idleCompaction":"off"}}}'`, keeping any instance the file already has, such as `devReplay`. Settings > Providers lists `Claude Limbase` with its **Limbase home**.
- **Turn.** From the project folder, run `node <worktree>/apps/server/src/bin.ts thread start --base-dir <worktree>/.t3 --provider claudeLimbase --model claude-haiku-5-5 --wait --json . "List the files here with your shell tool, then read one and quote it."`. It prints `"status":"completed"` and a reply. `node $T3V outcome sql "select json_extract(payload_json,'$.nativeMetadata.limbaseThreadId') from orchestration_v2_projection_provider_threads where thread_id='<thread id>'"` prints a `th_...` id, and `limbase thread show <th id>` (with `MEMBASE_HOME=<dir>/home`) shows the thread with `compact policy trigger 700000 target 100000`. `node .agents/skills/verify-t3code/scripts/limbase-turns.mjs <dir>/home <th id> t1` prints the capture cursor and the turn's prompt, tool calls and reply.
- **Install.** A view comes due only past the trigger. For a drive, lower `COMPACT_POLICY` in `apps/server/src/fork/Limbase.ts` in the worktree, never committed, to a trigger above the session's fixed context, for example `{ trigger: 110_000, target: 15_000 }`, and create the thread after the dev server restarts on that edit. Set a standing rule in the first turn, then have the agent read about 40,000 tokens of files across tool calls with `thread send`. `limbase-turns.mjs` then prints a cursor with `viewRevision` 1 or more. The turn completes, the reply still follows the rule, a T3 tool such as `mcp__t3-code__t3_project_list` still answers, the row's `nativeThreadRef.nativeId` is the new session id, and the project's folder under `~/.claude/projects/` holds one file for the thread. The next turn opens no new process: `grep -c '"query.open"'` on `.t3/userdata/logs/provider/events.<thread>.log` does not grow. Restore the policy before you commit.
- **Controls after an install.** On the same thread, in the browser: pick another reasoning level in the model picker while a turn runs. The events log gains a `query.apply_flag_settings` with the new `effortLevel`, and `query.open` does not grow. Have the agent launch a background subagent that reads in small pieces, hover its row under `Lineage`, and choose `Stop subagent <name>`. The events log gains a `query.stop_task`, the row reads `Stopped`, and `query.open` does not grow.
- **Retrieval.** `thread send` a prompt that asks the agent to call `mcp__limbase__get_turns` with `["t1"]` and say what the first turn set. The reply names the rule, and the events log holds `mcp__limbase__get_turns`.
- **Restart.** `node $T3V down`, `node $T3V up`, then `thread send` a turn. It completes, and the last `query.open` in the events log has `"resume"` equal to the row's stored session id.
- **Service restart.** Stop the lane's service by the PID in `<dir>/service.pid`, which the lane started, and run `lane.sh start <dir>`. `thread send` a turn. It completes, `limbase-turns.mjs` shows it captured after the earlier turns, and with the lowered policy above the next install still comes.
- **Edit.** Run three turns that each state a different fact (`remember fact 1: ALPHA`, then `BRAVO`, then `CHARLIE`) and change a file. In the browser, expand the second message's bubble, choose `Edit from here`, keep the restore choice the dialog offers, and send `which facts do you know?` as the edited message. The answer names ALPHA and neither later fact, the timeline ends at the kept turn and the new one, the files are as on a plain thread after the same edit, and `limbase-turns.mjs` holds nothing of the cut turns. The events log's next `query.open` has `"resumeSessionAt"`, and after the turn the row's `nativeConversationHeadRef` is null and `nativeThreadRef.nativeId` is a new session id. Send one more turn, restart the dev server and send another: each answers from the kept history.
- **Edit the first message.** Edit the first message of a Limbase thread the same way. The answer knows none of the old turns, and the provider-thread row is a new one whose `limbaseThreadId` differs from the old row's.
- **Edit that Limbase cannot make.** Stop the lane's service, edit a message and send it. After about three minutes the run fails with `limbase: stopped at capture: the thread did not open within the retry window. Edit the message again to retry.` `lane.sh start <dir>`. A plain send now fails with `... the rollback did not reach Limbase within the retry window. Edit the message again to retry.` Edit the same message again, and the turn answers from the kept history.
- **Refused edit.** With the lowered policy above, run `The code word for this turn is ROMEO`, then `TANGO`, then `/compact`, which the CLI answers with its own `<synthetic>` line, then reads until an install. Edit the message after `/compact`. Its place is that synthetic line from before the install, and the run fails with `limbase: stopped at view: rollback refused: anchor. Edit an earlier message to go on.` The row keeps its `nativeThreadRef.nativeId`, and `nativeConversationHeadRef` holds the place. Restart the dev server and send a plain prompt: it fails the same way. Edit the TANGO message, and the answer knows ROMEO alone. `overBound` and `failed` cannot be made on demand here; the host's real-CLI tests cover them.
- **Fail-out at a prompt.** Stop the lane's service by its PID, then `thread send` a turn. After about 90 seconds the run is `failed`. The thread shows the warning line `Operation stopped by hook: limbase: stopped at view: ...` and the provider error `limbase: stopped at view: view.due did not answer within the step's window`, which is the `error` turn item's `failure.message`. `lane.sh start <dir>`, and the next turn completes.
- **Fail-out at a tool boundary.** With Limbase up, `thread send` a turn that tells the agent to run `kill $(cat <dir>/service.pid)` with its shell tool in the foreground, then read a file. After about 90 seconds the run is `failed`, the sidebar card says `Failed`, and the thread shows `Provider error` with `limbase: stopped at capture: the step's records were not saved within the retry window`. Run `lane.sh start <dir>`, and the next turn completes. An agent asked to `sleep` hits this machine's shell hook, which blocks a chained sleep, so stop Limbase from the tool call itself.
- **Fork.** In the browser, choose `Fork from this response` on a reply and send a message in the fork. The fork's turn shows `Could not fork the source conversation natively (Limbase does not fork threads yet). Started a fresh session with its history.`, and its row has a new `limbaseThreadId`.
- **Plain.** Run the turn above with `--provider claudeAgent`. Its row has no `limbaseThreadId`, and its events log has no `mcp__limbase`. Drive `features/agent-turn.md` on it too.

- **Release build.** A dev server never runs the single-executable step, which rejects a static import of a file-backed package such as `zod` or `undici`. After `vp run --filter t3 build`, run `VP_NODE_VERSION=<engines.node> vp env exec --node <engines.node> node apps/server/scripts/cli.ts build-exe`. It ends `Built dist-exe/t3`, not `ServerCliExecutableImportError`. Before a merge, `~/lim-v2/bin/t3-v2-deploy <head>` builds the release and passes its smoke test. It never switches prod.

## Gotchas

- The Limbase service's socket path comes from `<home>/config/membase.json`, read at each open. A home whose path is long keeps its socket under `/tmp`.
- `thread send --json` exits 1 for a turn that Limbase stopped and prints the failure on its last line, not JSON.
- A dev server reads `apps/server/src/fork/Limbase.ts` again after an edit and restarts, which closes every live query. Edit the policy before you start the thread you drive.
- `GetTurns` ids are Limbase's own turn chunks, not T3 runs: one long T3 turn can span several.
