# Thread settings

The thread details panel shows the fork's own per-thread settings as rows at its foot, so a thread can be tuned without a release. The first is **Limbase compaction**, on a thread whose instance has a Limbase home: one row under **Context** (or in a short foot section when the context row is off) that shows the policy Limbase holds, such as `700k → 100k`, and opens a popover with two fields, **Compact at** and **Down to**. Each takes tokens, such as `700k`, or a share of the model's context window, such as `70%`. An empty field inherits, and its placeholder says what it inherits, from the instance or from Limbase's default for the model. A Claude instance with a Limbase home has the same two fields in Settings > Providers, below **Limbase home**, and every thread on the instance inherits them. A thread on any other instance shows no row.

## Sub-features

- `settings-card` shows the row only on a thread whose instance has a Limbase home, and sends no `forkSettings` request on any other thread. The row shows the policy Limbase holds now, or before the thread has a Limbase thread the one T3 would create it with. A value the thread sets itself is in the foreground and an inherited one is muted, a refused saved value or a value just refused turns it red and a warning amber, and a chevron says it opens. A value just refused keeps its draft and alert when the popover closes, by an outside click or Escape, and the row stays red, its name ending `, a value was not saved`, until the field is cleared or saved. The popover names the model and its window (`claude-haiku-5-5 · 1M window`), each empty field shows its inherited value as its placeholder, and a hint under the fields says what a blank field uses: `Blank uses the instance setting.`, `Blank uses Limbase's default for the model.`, or both. Escape closes it and gives focus back to the row. `docs/user/claude-limbase.md` says T3 owns the policy and when it puts its own back over one set with `limbase thread policy`.
- `settings-layout` keeps the panel's density what a plain thread's would be at the same height: the compaction and **Pinned as agent** rows sit at the panel's foot and are left out of the density measure, so they never push the machine row, **Commit**, **Automations** or **Previous agents** out, and on a short panel they are what scrolls away first.
- `settings-refresh` keeps a mounted row and its popover current. A model switch and the end of a turn show the new window, defaults and held policy with no reload. A model picked in the composer shows before the server has it, so the row refreshes again once the server confirms the pick, and names the picked model within a second. The row reads the policy Limbase holds only when it first shows a thread and when the thread's model changes, so a turn that changes nothing makes no Limbase call with the row shown. On a model the catalog knows, a refresh reads no provider turns, and on another it reads one.
- `settings-guard` refuses a value before it is sent: **Down to** under 24k, **Down to** not below **Compact at**, and a **Compact at** past the model's window. A value it cannot read asks for tokens or a share. Each alert belongs to its field, and going back to the saved value clears it. A saved value the current model refuses, such as a 500k **Compact at** after a switch to a 200k model, shows an alert that names the field and the policy Limbase keeps, after a reload too.
- `settings-save` saves a value, gives the Limbase thread its new policy at once, and shows Limbase's own refusal when the service refuses it. A save sends only the field it changes. While a save and its refresh are in flight, both fields are read-only and the popover shows `Saving…`. A refresh that fails or stalls past 15 s shows `Saved. The card could not reload its settings and is trying again.`, keeps the saved values and the lock, and retries, so no edit is lost or overwritten on a slow connection.
- `settings-owner` keeps drafts, alerts and a save in flight with the thread or instance they were typed for. Moving to another thread shows that thread's own values with no alert, and a commit there saves only to it.
- `settings-warning` warns that **Down to** at 300k or more turns Limbase's cold return off, and that an inherited **Compact at** past the window makes Limbase compact at its hard limit.
- `settings-instance` edits **Limbase: compact at** and **Limbase: down to** on a Claude instance with a Limbase home, and a thread gets the change at its next turn with no restart, even while its session stays open.
- `settings-seed` keeps 700k and 100k on each Claude instance that had a Limbase home when the server first started with this build, and on no instance made later.

## How to get to it (user POV)

- Open a thread on a Limbase instance. The **Limbase compaction** row is at the foot of the thread details panel, under **Context**. Click it to change the values.
- Settings > Providers, select a Claude instance with a **Limbase home**. **Limbase: compact at** and **Limbase: down to** follow **Limbase home**.

## Driving it with t3v

Preconditions:

- A Limbase lane and a Claude Code binary at the host's tested version, per `features/limbase-thread.md`.
- To drive `settings-seed`, add the Limbase instance before the first `up` of a fresh `.t3`, so the store's first creation sees it: `node $T3V settings providerInstances='{"claudeLimbase":{"driver":"claudeAgent","displayName":"Claude Limbase","config":{"limbaseHome":"<lane>/home","binaryPath":"<claude binary>","idleCompaction":"off"}}}'`, then `node $T3V up`.
- `node $T3V doctor` prints no `FAIL`, and a disposable git project is added with `node apps/server/src/bin.ts project add --base-dir <worktree>/.t3 <folder>`.
- One finished turn on the instance, from the project folder: `node <worktree>/apps/server/src/bin.ts thread start --base-dir <worktree>/.t3 --provider claudeLimbase --model claude-haiku-5-5 --wait --json . "Read README.md with your shell tool and quote it."`. `TH` is its `threadId`, and `LB` is the thread's Limbase id: `node $T3V outcome sql "select json_extract(payload_json,'\$.nativeMetadata.limbaseThreadId') from orchestration_v2_projection_provider_threads where thread_id='<TH>'"`. `POLICY` is `MEMBASE_HOME=<lane>/home pnpm exec limbase thread show <LB> | grep "compact policy"`, run from the lane's Limbase checkout.

- **Seed.** `node $T3V outcome sql "select scope, owner_id, settings_json from fork_settings"` prints the instance row with `compactAt` 700000 and `downTo` 100000 tokens, and the dev log has `fork-settings.seeded`. `POLICY` prints `trigger 700000 target 100000`. Add a second instance with a Limbase home and restart with `node $T3V down` and `node $T3V up`. That instance has no row.
- **Card.** Click the thread in the sidebar with `node $T3V browser click --text "<thread title>"`. `node $T3V browser wait --role button --name "Limbase compaction: 700k to 100k"` finds the row. Open it with `node $T3V browser click --role button --name-prefix "Limbase compaction"`: the popover names the model and its window, **Compact at** has the placeholder `Instance: 700k`, **Down to** has `Instance: 100k`, and the hint says `Blank uses the instance setting.` Every step below that fills a field opens the row first, and `browser press Escape` closes it.
- **Layout.** With **Usage limits** and **Context window** on (right-click the panel), size the window so a plain thread's panel is just `full` (`[data-thread-details-panel]` `data-density`, about 680 px tall with two automations and a previous agent). Open the Limbase thread at the same size: it is `full` too and shows the machine row, **Commit**, **Automations** and **Previous agents**, with the compaction row under **Context**. Pin it as an agent and **Pinned as agent** with **Unpin** joins the foot, set a little apart.
- **Guard.** `node $T3V browser fill --role textbox --name "Down to" --value "800k"`, then `browser press Enter`. The popover shows `Down to (800k) must be below compact at (700k).` and `POLICY` does not change. `20k` shows `Down to must be at least 24k.`, and `abc` shows `Write tokens, like 700k, or a share of the window, like 70%.`
- **Save.** Fill **Down to** with `15%` and press Enter. The row shows `700k → 150k` on a 1M window, with `150k` in the foreground, `POLICY` prints `trigger 700000 target 150000` before any turn runs, and `fork_settings` has the thread's row with `{"downTo":{"percent":15}}`.
- **Clear.** Fill **Down to** with an empty value and press Enter. The field shows its placeholder again, and the thread's row is gone from `fork_settings`.
- **Instance.** `node $T3V browser goto /settings/providers`, `browser click --role button --name "Select Claude Limbase"`, and `browser wait --text "Limbase: compact at"`. The two fields show `700k` and `100k`. Fill **Limbase: compact at** with `60%` and press Enter. `POLICY` does not change yet. Note `grep -c '"query.open"'` on the thread's events log, `.t3/userdata/logs/provider/events.<TH>.log`. Run a turn with `thread send --base-dir <worktree>/.t3 --wait --json <TH> "Say ok."` and `POLICY` prints `trigger 600000`, with the thread's own **Down to** kept, and the `query.open` count does not grow, so the change reached the live session.
- **Model switch.** Keep the panel open on a thread whose model has a 200k window, such as `claude-sonnet-4-6`. Pick `claude-haiku-5-5` in the composer's model picker and send `Say ok.`. Once `Working` leaves, the row shows the policy Limbase now holds and the popover names `claude-haiku-5-5 · 1M window`, with no reload. Fill **Compact at** with `500k`, which the 200k window refused, and it saves.
- **Refused after a switch.** With **Compact at** at `500k` on the 1M model, switch back to the 200k model and send a turn. The row turns red and the popover shows `Compact at (500k) must fit the model's 200k window. Limbase keeps 500k → <target> until you change it.`, and `POLICY` is unchanged. Reload with `browser goto` and the alert is still there. Clear **Compact at** and the alert goes.
- **Revert.** Fill **Compact at** with `2M` and press Enter, then fill it with its saved value and press Enter. The alert goes, and nothing is saved.
- **Unknown window.** On a thread whose last turns ran on `claude-haiku-5-5`, so its provider thread's context usage says 1M, add a custom model the catalog does not know to the instance, such as `claude-sonnet-4-5-20250929`, and pick it in the composer without sending. Within a second the popover names it with `claude-sonnet-4-5-20250929 · window unknown` and says `Nothing you save reaches Limbase until Claude reports the window.` Fill **Down to** with `15%` and press Enter. `fork_settings` has `{"downTo":{"percent":15}}`, and `POLICY` does not change. The first turn on the model ends with the popover naming its `200k window`, and `POLICY` still unchanged. The next turn sets `POLICY` to `trigger 700000 target 30000`. A custom model the gateway refuses, such as `claude-haiku-4-5-20251001`, fails each turn with `unknown provider for model` and stays unknown.
- **Reads.** Relay the lane's Limbase socket through a logger of `GetThread`, `SetCompactPolicy` and `CreateThread` frames, as `scratch/thread-settings-r4/policy-proxy.py` in the run does, and count `forkSettings.getThread` frames on the page's WebSocket. With the row shown on a Limbase thread, send `Say ok.` on an unchanged model. The relay logs no frame for the turn. A thread on an instance with no Limbase home sends no `forkSettings.getThread` frame for a turn.
- **Stalled refresh.** Hold the reply to the first `forkSettings.getInstance` after a `forkSettings.setInstance` for 22 s with `page.routeWebSocket`. Fill **Limbase: compact at** with `640k` and press Enter. After 15 s the instance rows show `Saved. The card could not reload its settings and is trying again.`, both fields stay read-only on `640k`, and the fields unlock once a retry lands. Then fill **Limbase: down to** with `95k`. Its `forkSettings.setInstance` frame names only `downTo`, and `fork_settings` holds `640000` and `95000`.
- **Owner.** Open a thread on a 1M model and one on a 200k model, so both are cached. On the 1M thread fill **Compact at** with `2M` and press Enter, then click the 200k thread in the sidebar. Its popover shows its own empty **Compact at** and no alert. Fill `150k` there and press Enter, and `fork_settings` has the 200k thread's row alone.
- **Slow save.** Delay the server's reply to the first save by 1.5 s with Playwright's `page.routeWebSocket("**/ws*")`, holding the `Exit` frame whose `requestId` is the first `forkSettings.setInstance` request's `id`. On the instance, fill **Limbase: compact at** with `650k` and press Enter. Both fields are read-only and `Saving…` shows until the reply and the refresh land. Then fill **Limbase: down to** with `90k`, and `fork_settings` holds both.
- **Hand edit.** `MEMBASE_HOME=<lane>/home pnpm exec limbase thread policy --trigger 490000 --target 140000 <LB>`. A turn on the live session leaves it, because T3 does not read Limbase at each turn. An instance edit from `60%` to `600k` on a 1M model resolves to the same tokens, so it leaves the hand edit too. Stop and start the dev server, and the next turn puts the resolved policy back. A hand-set `--cold-size 0` with the same tokens is put back the same way.
- **Plain.** A thread on a Claude instance with no Limbase home shows no **Limbase compaction** row and sends no `forkSettings.getThread`, and its instance has no Limbase rows.

## Gotchas

- The seed runs only when the server first creates the `fork_settings` table. On a `.t3` that already has the table, adding an instance never seeds it, which is the point. To drive the seed again, use a fresh `.t3`.
- The popover's window comes from the Claude model catalog, else from the thread's latest turn with token usage, when that turn ran on the thread's model. It never takes a window measured on another model, so the provider thread's last context usage from before a switch does not count. A model that is not in the catalog shows `<model>, window unknown until Claude reports it. Nothing you save reaches Limbase until then.` until a turn on it reports one, and the thread's policy is set at the next turn. Claude Code reports a `[1m]` model's window under its bare id, so a custom `claude-haiku-5-5[1m]` gets the window reported for `claude-haiku-5-5` after its first turn. On an instance whose fields are `50%` and `15%`, that turn leaves `POLICY` at `trigger 500000 target 150000` and the card names `claude-haiku-5-5[1m], 1M window.`
- Limbase's own refusal reaches the popover as `Limbase: the service refused the compaction policy (limbase call failed: <tag>)`. The host's call reports only the error's tag, not its text.
- A save applies at once only on a thread that already has a Limbase thread. On a new thread the policy goes into Limbase's `CreateThread` at its first turn.
