## What the fork adds

- **The preview browser keyring fix** (in `apps/server/src/htmlRender/headlessChrome.ts`). The headless shell behind `html_preview` and `html_render` starts with `--password-store=basic`. Without it, Chrome asks the desktop keyring over D-Bus before its first network request. On a headless Linux host that call can wait forever on a prompt to create a keyring, so every capture times out after 20 seconds. The Browser panel already passes the flag through Playwright.

Prod has one such instance, `cursor-cloud`, configured in settings rather than code. - **The MCP placement test** (commit `fc6ad78149`, in `packages/provider-cursor/src/server/adapter.cloud.test.ts`). A cloud run never gets it, because the VM cannot reach this machine. Upstream #15875 moved the server off sends. This test is the one fact the 3238 merge was safe because of.
- **Thread workflows** (PRs #10, #12 and #13; PR #11 was folded into #12). The user guide is `docs/user/thread-workflows.md`. A thread can carry a checklist workflow. The agent works through it with the `thread_workflow_*` MCP tools, the user drives it over the `threadWorkflow.*` RPC methods, and an open workflow refuses settle, archive and delete. `threadWorkflowsEnabled` in server settings turns it on, and it is off by default. Turning it off stops new workflows, but an open one keeps blocking. The bypass for that is `threadWorkflowEnforcementDisabled` in server settings, or `T3CODE_THREAD_WORKFLOW_ENFORCEMENT=off` in the server's environment when settings cannot be edited. Either one stops every workflow blocking, with no rebuild. The module never stops a turn, traps a thread, or stops the server starting. A corrupt log, an unreadable store, or a fault in a hook gives no turn note and no blocker, and logs why. Core bounds each hook call itself as well, so a fault that escapes the module's own containment still costs only the note or the blocker. The module's disk work runs one operation at a time under one permit, so a stalled disk under it holds at most one of Node's four worker threads; a later module operation waits within its own deadline and answers `store_unavailable`. The code is ours in `apps/server/src/threadWorkflow/`, `apps/server/src/mcp/toolkits/threadWorkflow/`, `apps/server/src/orchestration-v2/ThreadHooks.ts` and `packages/contracts/src/threadWorkflow.ts`. - **Restart-held queues resume** (in `apps/server/src/fork/HeldQueueResumer.ts`, with its tests in `apps/server/src/fork/HeldQueueResumer.test.ts`). Upstream holds every queued message at a restart and waits for **Resume**, by design (upstream `6c9d827a41`, "require explicit consent before draining them"). This fork resumes a queue that only a restart held, once the thread is quiet again and its last turn ended well, when **Continue threads after restarts** is on for the project. A queue held by **Stop**, a provider failure, a missing worktree or a disabled instance stays held, and so does one whose last turn was cut, stopped or failed, whose thread waits on an answer or a secret, that the user stopped after the restart held it, or whose hold is older than the outbox's seven-day retention. It reads a bounded tail of the thread's event stream on the server's read-only connection. It reads the hold's cause from the stored command id of the event that set `queueHeld`, because the flag has no reason field. The upstream files we changed are `apps/server/src/server.ts` (one registration line), `docs/user/composer.md` and `docs/user/updating.md`.
- **Group chat** (PR #16 adds the section shell, PR #18 the engine). A **Group chat** item after **Usage** in the sidebar footer opens `/group-chat`, which swaps in its own group sidebar the way Settings does. A group is a set of T3 threads. A message to a group becomes one envelope per recipient, sent into that member thread's own queue with `mode: "queue"`, never steered, so Stop, Resume, edit and reorder in T3 work on it like any queued message. The reply is the last assistant message of the run T3 recorded. The module keeps its own database, `<stateDir>/group-chat/groupchat.sqlite`, with its own migrations table, so it never joins T3's migration sequence, and it recovers every open delivery from that store alone at boot. It reaches threads only through `apps/server/src/groupChat/threadPort.ts` over the server's `ThreadManagementService`, and registers no `ThreadHooks`. `T3CODE_GROUP_CHAT=off` in the server's environment turns it off: it opens no store and answers every request with `GroupChatUnavailable` (`disabled`). A store that cannot open or migrate is logged and answers `store_unavailable`, and the server still starts. The code is ours in `apps/server/src/groupChat/`, `apps/web/src/groupChat/`, `apps/web/src/routes/group-chat*.tsx` and `packages/contracts/src/groupChat.ts`. The upstream files we changed are `apps/web/src/components/sidebar/SidebarChrome.tsx`, `apps/web/src/components/sidebar/mainAppLocation.ts`, `apps/web/src/components/AppSidebarLayout.tsx`, `apps/web/src/routeTree.gen.ts` (regenerated), `packages/contracts/src/environmentHttp.ts` (the `groupChat` group, whose `dispatch` endpoint declares the module's result and typed refusals) and `apps/server/src/server.ts`. `mainAppLocation.ts` also keeps the last main-app location in the tab's `sessionStorage`, so Back from Group chat, Settings or Usage returns to that thread after a reload. Upstream keeps it only in memory, so Back after a reload opens a new draft. External members (GC6) are REST and webhook agents reached over HTTP, in `apps/server/src/groupChat/transports/`, `hooks.ts` and `reach.ts`. Each one is its own lane. Every request for a delivery carries the delivery id as `Idempotency-Key` for life and the request count as `X-Gchat-Attempt`, transient failures retry with backoff up to a bounded budget, a 4xx fails the delivery until Retry, and a webhook that never calls back fails after 90 seconds while a late callback still lands. Their hook URLs live under `/api/hooks/group-chat/`, so the server's untraced-path rule covers them, and the token rides in the query string, which the request log strips. The hook route caps the body at 1 MB while reading it, compares tokens in constant time, rate-limits each hook, and requires an `X-Signature` HMAC once the server is reachable beyond loopback (a non-loopback `--host`, or the T3 Connect link marker in the secret store); on such a server an external member cannot be created without a secret. Secrets (endpoint headers, the shared secret, the inbound token) stay in `groupchat.sqlite` and never reach the contracts, the event stream or the browser; the inbound URL is read on demand through the `member.inboundUrl` command.

## Branches and merges

- `main` is the upstream nightly we last synced plus the fork's commits. Every change reaches `main` through a PR.
- Work goes on a short-lived branch: `fix/...`, `feature/...`, `sync/upstream-nightly-<n>`. T3 creates `t3/...` branches for its own worktrees. Leave branches that another thread owns alone.
- Merge every PR with a merge commit: `gh pr merge <n> --merge`. Never squash and never rebase `main`. A squash flattens upstream's history, so the next sync conflicts on every file upstream touched since. GitHub still allows squash and rebase on this repository, so nothing stops a wrong merge button but this rule.
- The fork's `origin` carries one old nightly tag, `v0.0.46-nightly.20261011.2980`. Upstream's tags come from `git fetch upstream --tags`. Without them, `git describe` names a build of today's `main` after that old tag.
- `gh` resolves this repository to `liminal-ai/t3code-v2` through `remote.origin.gh-resolved` in the shared git config. Without that line, `gh` picks the `upstream` remote and a bare `gh pr create` opens the PR on `pingdotgg/t3code`. If `gh repo view --json nameWithOwner` ever prints `pingdotgg/t3code`, run `gh repo set-default liminal-ai/t3code-v2`.

## Before you push, open a PR, or merge

1. Do not change any `AGENTS.md` or `CLAUDE.md`, including this repository's, until Lee approves the exact text.
2. Run `gh repo view --json nameWithOwner` and check that it prints `liminal-ai/t3code-v2`.
3. If the change touches a file in [Seams to re-check](#seams-to-re-check), run the tests listed there.
4. Follow upstream's `AGENTS.md` for everything else: conventional commit titles, focused tests, no repo-wide checks.
5. Get an independent verdict from a model family other than the author's before you merge. The pstack Shipping playbook covers how.
6. Merge with `--merge`. A merge changes nothing in prod until a cutover, and only Lee runs or approves a cutover.

## Sync from upstream

Sync to a published nightly tag, not to upstream `main`. A nightly is a build upstream shipped. `main` carries unreleased work.

1. Fetch and pick the tag:

   ```bash
   git fetch upstream --tags
   git tag -l 'v*-nightly.*' --sort=-creatordate | head -5
   ```

2. List what upstream changed in the files we changed. Read each of those commits before you merge.

   ```bash
   OLD=v0.1.1-nightly.20261017.3238   # the "Last synced" tag above
   NEW=<new tag>
   git log --oneline $OLD..$NEW -- $(git diff --name-only $OLD main)
   ```

3. Merge on a branch:

   ```bash
   git switch -c sync/upstream-nightly-<n> main
   git merge --no-ff $NEW
   ```

   Resolve each conflict so that upstream's new behavior and ours both survive. If upstream now does what one of our changes did, take upstream's version and delete ours.

4. Verify three things. Upstream owns testing upstream, so do not re-test upstream features.
   - Our code: the provider-cursor tests, with the commands in [Seams to re-check](#seams-to-re-check).
   - The seams: the tests in [Seams to re-check](#seams-to-re-check), and the content check that the merged tree is upstream plus our diff and nothing else. Compare `git diff $NEW <merge>` with `git diff $OLD main`. The only differences should be the conflict resolutions you made.
   - The deployment: build a release (see [Build a release](#build-a-release)) and run it as a throwaway T3, never against prod. See [Test live without touching prod](#test-live-without-touching-prod).
5. Open the PR against `main`. Set "Last synced" in this file to the new tag in the same PR.
6. Have a reviewer from the other model family verify it, then merge with `--merge`. If the merge commit carries a test that the next commit fixes, that is fine. `main`'s first-parent history stays green because the PR lands as a merge commit.
7. Stop. The cutover is a separate step that Lee runs or approves.

Bot reviews do not cover a sync. Bugbot refused PR #4 at 42,105 lines, and Codex reviews a PR once, not after each push.

## Build a release

`~/lim-v2/bin/t3-v2-deploy <ref>` builds `<ref>` from the main checkout `~/lim-v2/code/t3code-v2` into the same linux-x64 `t3` archive upstream ships. It names the release `t3-<nightly>-lim.<sha>-linux-x64` from `git describe --tags --match 'v*-nightly.*'`, so run `git fetch upstream --tags` in that checkout first. It unpacks the release into `~/lim-v2/service/t3code/prod/releases/` and smoke-tests it on port 13995.

The script never switches prod. It ends by printing the `t3-v2-cutover` command for the new release, with its sha256.

## Cut over

Lee runs or approves every cutover.

1. Run `~/lim-v2/bin/t3-v2-cutover <release-name> <sha256-of-t3>`. The restart ends every T3 thread on prod, including the one that starts it. So run it from a terminal, or from a T3 thread as a detached `systemd-run --user` job.
2. The script never waits for prod to go idle, because it may never be idle. It lists the runs the restart interrupts, which T3 resumes after the update, and goes ahead. It backs up `statev2.sqlite` into `prod/data/backups/`, switches `prod/current`, restarts `t3code-v2-prod`, and checks that the new binary answers 200 on 13987. If the check fails, it switches back once.
3. After the switch, whether the check passed or failed, it starts `t3-v2-triage`, a headless Claude Code agent outside T3. The agent writes `report.md` in `~/lim-v2/notes/t3-v2-cutover/<time>-<release>/`.
4. Read the report. Reload every open T3 browser tab. A tab keeps the web client it loaded before the restart, and an old client can reject values the new server sends. The report ends with that reminder.
5. Keep the backup. A release can rewrite data on first start. 3238 compacted 54,269 events, so its backup is the only uncompacted copy.

To roll back, point `prod/current` at the previous release and restart the unit. `facts.env` in the run folder names the previous release. A rollback runs the old binary on data the new one may have migrated or compacted. Nobody has tested that for 3238.

## Fixes owed upstream

None are open. Worktree isolation for delegated tasks (pingdotgg/t3code#19102) was raised during the 3238 sync. It is merged upstream and shipped in 3238, so the fork owes nothing there. pstack-lim could use it in place of the `git worktree add` steps its skills ask helpers to run, which is a change for that repository.

Two gaps could go upstream. The first is the preview browser keyring fix in "What the fork adds", a one-line change.

The second is in the web client. It warns when the server is older than the client (`apps/web/src/versionSkew.ts`), but not when the client is older than the server, so a tab left open across a server update keeps an old client until it happens to reload. The fork covers it with the reload line in the cutover report.
