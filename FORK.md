## Branches and merges

- `main` is the upstream tag we last synced plus the fork's commits. Every change reaches `main` through a PR.
- Work goes on a short-lived branch: `fix/...`, `feature/...`, `sync/upstream-<tag>`. T3 creates `t3/...` branches for its own worktrees. Leave branches that another thread owns alone.
- Merge every PR through the merge gate, with a merge commit: `~/.agents/skills/poteto-mode/scripts/merge-gate/merge-gate --repo liminal-ai/t3code-v2 --pr <n> --method merge`. The gate checks the PR's checks, review threads, the independent verdict and Lee's approval of any instruction-file text, then merges. Never merge a PR with `gh` yourself, never squash and never rebase `main`. A squash flattens upstream's history, so the next sync conflicts on every file upstream touched since. GitHub still allows squash and rebase on this repository, so nothing stops a wrong merge button but this rule.
- The fork's `origin` carries one old nightly tag, `v0.0.46-nightly.20261011.2980`. Upstream's tags come from `git fetch upstream --tags`. Without them, `git describe` names a build of today's `main` after that old tag.
- `gh` resolves this repository to `liminal-ai/t3code-v2` through `remote.origin.gh-resolved` in the shared git config. Without that line, `gh` picks the `upstream` remote and a bare `gh pr create` opens the PR on `pingdotgg/t3code`. If `gh repo view --json nameWithOwner` ever prints `pingdotgg/t3code`, run `gh repo set-default liminal-ai/t3code-v2`.

## Before you push, open a PR, or merge

1. Do not change any `AGENTS.md` or `CLAUDE.md`, including this repository's, until Lee approves the exact text.
2. Run `gh repo view --json nameWithOwner` and check that it prints `liminal-ai/t3code-v2`.
3. If the change touches a file in [Seams to re-check](#seams-to-re-check), run the tests listed there.
4. `AGENTS.md` is owned by the fork and points here. Upstream's agent rules do not apply to this repository. Keep conventional commit titles and focused tests, and run no repo-wide checks.
5. Get an independent verdict from a model family other than the author's before you merge. The pstack Shipping playbook covers how.
6. The verdict drives the change through the verify skill, `.agents/skills/verify-t3code/`.
7. Merge through the merge gate with `--method merge`. `.agents/merge-brief.md` lists this repository's gates, and the gate prints it on every run. A merge changes nothing in prod until a cutover, and only Lee runs or approves a cutover.

## Sync from upstream

1. Fetch the tag. Upstream cuts each stable tag on the same commit as a nightly (`v0.1.5` is `v0.1.5-nightly.20261029.3877`). `t3-v2-deploy` finds that nightly with `git describe --match 'v*-nightly.*'` and names the build after the stable tag on its commit, so a `v0.1.5` merge builds as `t3-0.1.5-lim.<sha>`.

   ```bash
   git fetch origin
   git fetch upstream --tags
   git tag -l 'v*' --sort=-creatordate | head -10
   git tag --points-at <stable tag>   # the nightly on the same commit
   ```

   Every later step works from `origin/main`, never local `main`. On the 3824 sync local `main` was stale behind PR #42, and the first merge started from it.

2. List what upstream changed in the files we changed. Read each of those commits before you merge.

   ```bash
   OLD=v0.1.5   # the "Last synced" tag above
   NEW=<new tag>
   git log --oneline $OLD..$NEW -- $(git diff --name-only $OLD origin/main)
   ```

3. Merge on a branch:

   ```bash
   git switch -c sync/upstream-<tag> origin/main
   git merge --no-ff $NEW
   ```

   Resolve each conflict so that upstream's new behavior and ours both survive. If upstream now does what one of our changes did, take upstream's version and delete ours.

   A file that merges with no conflict can still break the fork. Upstream #26238 dropped `settings` from the Cursor driver's `makeCursorAdapterV2` call, git applied `packages/provider-cursor/src/server/driver.ts` cleanly, and that broke the handoff of each instance's settings, which carry **Runs on**, to the fork's adapter. The adapter still requires `settings`. Without them it fails to start, and with default settings in their place a `cursor-cloud` instance runs on this machine. The 3824 sync restored the argument, and `driver.test.ts` "builds a %s adapter from the instance's Runs on setting" now pins it. So read the step 2 commits and run the seam tests even when every file merges clean.

4. Verify three things. Upstream owns testing upstream, so do not re-test upstream features.
   - Our code: the provider-cursor tests, with the commands in [Seams to re-check](#seams-to-re-check).
   - The seams: the tests in [Seams to re-check](#seams-to-re-check), and the content check that the merged tree is upstream plus our diff and nothing else. Compare `git diff $NEW <merge>` with `git diff $OLD origin/main`. The only differences should be the conflict resolutions you made.
   - The deployment: build a release (see [Build a release](#build-a-release)) and run it as a throwaway T3, never against prod, with one real turn on Cursor, Claude and Codex. 5. Open the PR against `main`. Set "Last synced" in this file to the new tag in the same PR.
6. Have a reviewer from the other model family verify it, then merge with `--merge`. If the merge commit carries a test that the next commit fixes, that is fine. `main`'s first-parent history stays green because the PR lands as a merge commit.
7. Stop. The cutover is a separate step that Lee runs or approves.

## Build a release

`~/lim-v2/bin/t3-v2-deploy <ref>` builds `<ref>` from the main checkout `~/lim-v2/code/t3code-v2` into the same linux-x64 `t3` archive upstream ships. It names the release `t3-<tag>-lim.<sha>-linux-x64` after the nightly that `git describe --tags --match 'v*-nightly.*'` finds, or after the stable tag on that nightly's commit, so run `git fetch upstream --tags` in that checkout first. It unpacks the release into `~/lim-v2/service/t3code/prod/releases/` and smoke-tests it on port 13995.

Since upstream #26912 the Linux archive carries `lib/libatomic.so.1` and sets `t3`'s RUNPATH to it with `patchelf`, so the build host needs the `patchelf` and `libatomic1` packages. Without `patchelf`, `build-cli-archive.ts` stops with `spawn patchelf ENOENT`. This machine got `patchelf` during the `v0.1.5` sync.

The script never switches prod. It ends by printing the `t3-v2-cutover` command for the new release, with its sha256.

## Cut over

Lee runs or approves every cutover.

1. Run `~/lim-v2/bin/t3-v2-cutover <release-name> <sha256-of-t3>`. The restart ends every T3 thread on prod, including the one that starts it. So run it from a terminal, or from a T3 thread as a detached `systemd-run --user` job.
2. The script never waits for prod to go idle, because it may never be idle. It lists the runs the restart interrupts, which T3 resumes after the update, and goes ahead. It backs up `statev2.sqlite` into `prod/data/backups/`, switches `prod/current`, restarts `t3code-v2-prod`, and checks that the new binary answers 200 on 13987. If the check fails, it switches back once.
3. After the switch, whether the check passed or failed, it starts `t3-v2-triage`, a headless Claude Code agent outside T3. The agent writes `report.md` in `~/lim-v2/notes/t3-v2-cutover/<time>-<release>/`.
4. Read the report. Reload every open T3 browser tab. A tab keeps the web client it loaded before the restart, and an old client can reject values the new server sends. The report ends with that reminder.
5. Keep the backup. A release can rewrite data on first start. 3238 compacted 54,269 events, so its backup is the only uncompacted copy.

To roll back, point `prod/current` at the previous release and restart the unit. `facts.env` in the run folder names the previous release. A rollback runs the old binary on data the new one may have migrated or compacted. Nobody has tested that for 3238.

## Fixes owed upstream

None are open. Worktree isolation for delegated tasks (pingdotgg/t3code#19102) was raised during the 3238 sync. It is merged upstream and shipped in 3238, so the fork owes nothing there. pstack-lim could use it in place of the `git worktree add` steps its skills ask helpers to run, which is a change for that repository.

Three gaps could go upstream. The first is the preview browser keyring fix in "What the fork adds", a one-line change. The second is the pair of Personal Team fixes in `apps/mobile/app.config.ts`: upstream's `T3CODE_IOS_PERSONAL_TEAM=1` path still writes `aps-environment` into the entitlements, because its strip plugin is registered last and so runs first, and still pins `appleTeamId` to T3's team, which a Personal Team cannot sign for.

The third is in the web client. It warns when the server is older than the client (`apps/web/src/versionSkew.ts`), but not when the client is older than the server, so a tab left open across a server update keeps an old client until it happens to reload. The fork covers it with the reload line in the cutover report.
