- **Restart-held queues resume** (in `apps/server/src/fork/HeldQueueResumer.ts`, with its tests in `apps/server/src/fork/HeldQueueResumer.test.ts`). Upstream holds every queued message at a restart and waits for **Resume**, by design (upstream `6c9d827a41`, "require explicit consent before draining them"). This fork resumes a queue that only a restart held, once the thread is quiet again (no active run, and no restart continuation or checkpoint capture still pending) and its last turn ended well, when **Continue threads after restarts** is on for the project. A queue held by **Stop**, a provider failure, a missing worktree or a disabled instance stays held, and so does one whose last turn was cut, stopped or failed, whose thread waits on an answer or a secret, that the user stopped after the restart held it, or whose hold is older than the outbox's seven-day retention. A queue whose next run's provider stopped on a usage limit with a reported reset still ahead stays held until that reset, then resumes, the same as core's own automatic start. Upstream also releases every held queue when the user sends a message from web or mobile (upstream `62d98096ca`, #21473), and the two never start a queue twice: a send writes `queueHeld: false` under its own command id, which the resumer reads as a release, and a resume that lands after a send only rewrites a flag that is already off. It reads a bounded tail of the thread's event stream on the server's read-only connection. It reads the hold's cause from the stored command id of the event that set `queueHeld`, because the flag has no reason field. It picks the provider a held run starts on with upstream's `followsCurrentConversation`, which the fork exports from `Orchestrator.ts`. The upstream files we changed are `apps/server/src/server.ts` (one registration line), the `export` of `followsCurrentConversation` in `apps/server/src/orchestration-v2/Orchestrator.ts`, the keep rule in `apps/server/src/orchestration-v2/ProjectionMaintenance.ts`, `docs/user/composer.md` and `docs/user/updating.md`.

- **Delegated requests time out** (in `apps/server/src/fork/DelegatedRequestTimeout.ts`, with its tests in `apps/server/src/fork/DelegatedRequestTimeout.test.ts`). A delegated child can wait forever on a permission prompt or a question that no human will answer. A child in Supervised mode (`approval-required`) asks before each write, and no agent can approve it. Claude Code blocks an `rm` whose path is built from a loop variable outright, even under bypass permissions, so that command fails rather than waits. Upstream wakes the parent only for a child's question, and nothing upstream times a request out. This fork wakes the parent at once when an app-owned child raises an approval. The wake's notification has outcome `unknown`, because upstream drops a `delegated_task` wake with outcome `updated` that matches no pending child question. The message holds the prompt and the reason the provider gave, says an agent cannot approve it and the user can, and says when T3 will decline it. Upstream's own wake still covers questions. A request on a delegated child that is still pending ten minutes after it was raised gets a note that no human is available. A Claude approval is declined with the note as its feedback, which the model reads as the tool's result after upstream's `The user declined this tool call and said:` (upstream `365a62aa84`), so the note says nobody approved it in ten minutes, that no human is watching and an agent cannot approve it, and that T3 declined it on the user's behalf. It quotes Claude's reason, which often names the fix (a literal path). A Codex approval is declined with Codex's own fixed text, because Codex takes no feedback. A question gets the note as the answer to each of its questions. The child then works around it, or stops and says in its final message what it needed. A top-level thread, a fork and a provider-native subagent are never touched. The deadline is the request's `createdAt`. A sweep at start and every minute re-arms it, so after a restart a question that recovery kept is still answered, and the answer becomes the child's next message. A pending approval does not survive a restart, because recovery expires it. A child that a linked environment launched here through `delegate_task` carries `delegatedFrom` on its thread, so it gets the deadline too, with no parent here to wake. The parent's own server cannot see that request (`readRemoteTask` reports no question or approval), so only the server that runs the child can answer it. `T3CODE_DELEGATED_REQUEST_TIMEOUT=off` in the server's environment turns the module off. The verify skill's `features/delegated-requests.md` drives it. The upstream files we changed are `apps/server/src/server.ts` (one registration line) and `docs/user/thread-sidebar.md`.

Its row, **Limbase compaction**, shows the policy Limbase holds for the thread, or before the thread has a Limbase thread the one T3 would create it with, such as `700k → 100k`, with a value the thread sets itself in the foreground and an inherited one muted, red when a saved value is refused and amber on a warning. Its popover has the two fields side by side, the model and its window, the notices, and a hint that says what a blank field uses. It shows on a thread whose instance has a Limbase home, and the web asks for it on no other thread. It also shows on a Claude instance with a Limbase home, as **Limbase: compact at** and **Limbase: down to** below **Limbase home** in Settings > Providers. T3 resolves the policy and Limbase stores tokens. Each field is the thread's value, else the instance's, else Limbase's own default for the model's class (`PROFILES` and `profileFor`, imported from the vendored host and never copied). A share becomes tokens with the window that the adapter's `claudeContextWindow` gives: the catalog's, else the one the CLI reported. Claude Code reports the window of a `[1m]` model under its bare id, so a custom `claude-haiku-5-5[1m]` gets the window reported for `claude-haiku-5-5`. The popover shows the catalog's window. Only when the catalog has none does the server read a provider turn, the one whose token usage the active provider thread updated last, and it takes the window that turn was measured against when the turn ran on the thread's model. It never takes a window measured on another model, such as the active provider thread's last context usage after a switch. Without one the popover says the window is unknown and that nothing reaches Limbase until Claude reports it, and a save is kept but sends Limbase nothing. The guards are in the one resolver that the web, the save path, the query open and the turn share. **Down to** is at least 24k and below **Compact at**, a **Compact at** set on the thread fits the window, a target of 300k or more warns that Limbase turns cold return off, and an inherited **Compact at** past the window warns that Limbase compacts at its hard limit and is still sent, as 700k always was on a 200k-class model. At each query open `Limbase.queryFor` resolves the thread's policy, reads the Limbase thread's own with `GetThread`, and calls `SetCompactPolicy` only when they differ. With no window yet it leaves Limbase's policy alone and sets it once the CLI has reported one. A live session is reused across turns, so the adapter's `startTurn` also calls `Limbase.applyTurnPolicy` at every turn, after `openQuery`. It resolves the policy again for the turn's model and calls Limbase only when the result differs from the policy T3 last read or set on that Limbase thread. T3 keeps that policy in memory, so a turn that changes nothing costs no round trip, and the first turn after a restart reads Limbase again. A guard that fails at a query open or a turn, an unreadable store, or Limbase's refusal leaves Limbase's policy as it was and logs a warning, and the turn runs. `CreateThread` sends the same policy. A thread value saved in the popover is applied to its Limbase thread at once, so Limbase's refusal reaches the popover. An instance value, and a model switch inside a live session, reach each thread at its next turn. The settings live in one table, `fork_settings` in `statev2.sqlite`, keyed by scope (`thread` or `instance`) and owner id, with every group of one owner in one JSON row. The fork creates it with `CREATE TABLE`, outside upstream's numbered migrations, so a sync never collides with it. Its first creation is the one moment that tells an instance from before compaction was a setting from one made after, so in that transaction it writes `compactAt` 700k and `downTo` 100k onto every Claude instance with a Limbase home, and those instances keep today's `COMPACT_POLICY` until someone changes it. An instance made later inherits Limbase's defaults. Reads and writes go through four WS RPCs: `forkSettings.getThread` and `getInstance` need `orchestration:read`, `setThread` needs `orchestration:operate`, and `setInstance` needs `providers:manage`, as editing the instance does. A fork does not copy a thread's settings, and mobile does not show them. T3 owns each Limbase thread's policy. A policy set by hand with `limbase thread policy` is an operator's action, and T3 puts its resolved policy back at the next query open, or at an earlier turn whose resolved policy changed, as a model switch or a setting that resolves to different tokens makes it. A turn whose resolved policy is the one T3 last read or set makes no Limbase call, so T3 does not read Limbase at each turn to catch a hand edit. A held policy that names `cold` differs from T3's, which never sends one, so a hand-set cold return is put back too. `docs/user/claude-limbase.md` says T3 owns the policy and when it puts its own back. A mounted row refreshes when its thread's instance, model or provider thread changes and when a turn ends, so it shows the new window, defaults and held policy with no reload. A model picked in the composer shows before the server has it, so the row refreshes again once the thread has no pending optimistic update. The row reads the policy Limbase holds with `GetThread` when it first shows a thread and when the thread's model changes, which it tells the server by sending the model of the view it already shows. Any other refresh gets the policy T3 last read or set on that Limbase thread, so a turn that changes nothing reads no Limbase with the row shown. A save names only the field it changes, and the server merges it into the stored value, so an edit never sends a stale value of the other field. Until the refresh after a save lands, the row and its popover show the view the server acknowledged the save with, both fields are read-only, and the popover shows `Saving…`. A refresh that fails or takes more than 15 s says the popover is trying again, and it tries every 2 s, so the fields never unlock onto values from before the save. The instance rows do the same. Drafts, alerts and a save in flight belong to one thread or instance, so moving to another starts its row fresh, and a commit writes only to the owner it was typed for. An alert belongs to its field, and going back to the saved value clears it. A saved thread value the current model refuses, such as a 500k **Compact at** on a 200k model, shows an alert that names the field and the policy Limbase keeps until it changes. ## Branches and merges

- `main` is the upstream tag we last synced plus the fork's commits. Every change reaches `main` through a PR.
- Work goes on a short-lived branch: `fix/...`, `feature/...`, `sync/upstream-<tag>`. T3 creates `t3/...` branches for its own worktrees. Leave branches that another thread owns alone.
- Merge every PR through the merge gate, with a merge commit: `~/.agents/skills/poteto-mode/scripts/merge-gate/merge-gate --repo liminal-ai/t3code-v2 --pr <n> --method merge`. The gate checks the PR's checks, review threads, the independent review, the lead's acceptance and Lee's approval of any instruction-file text, then merges. Never merge a PR with `gh` yourself, never squash and never rebase `main`. A squash flattens upstream's history, so the next sync conflicts on every file upstream touched since. GitHub still allows squash and rebase on this repository, so nothing stops a wrong merge button but this rule.
- The fork's `origin` carries one old nightly tag, `v0.0.46-nightly.20261011.2980`. Upstream's tags come from `git fetch upstream --tags`. Without them, `git describe` names a build of today's `main` after that old tag.
- `gh` resolves this repository to `liminal-ai/t3code-v2` through `remote.origin.gh-resolved` in the shared git config. Without that line, `gh` picks the `upstream` remote and a bare `gh pr create` opens the PR on `pingdotgg/t3code`. If `gh repo view --json nameWithOwner` ever prints `pingdotgg/t3code`, run `gh repo set-default liminal-ai/t3code-v2`.

## Sync from upstream

1. Fetch the tag Lee picks, nightly or stable. Upstream cuts each stable tag on the same commit as a nightly (`v0.1.5` is `v0.1.5-nightly.20261029.3877`). `t3-v2-deploy` finds the nightly with `git describe --match 'v*-nightly.*'` and names the build after the stable tag on its commit when there is one, so a `v0.1.5` merge builds as `t3-0.1.5-lim.<sha>` and a `v0.1.7-nightly.20261101.4016` merge builds as `t3-0.1.7-nightly.20261101.4016-lim.<sha>`.

   ```bash
   git fetch origin
   git fetch upstream --tags
   git tag -l 'v*' --sort=-creatordate | head -10
   git tag --points-at <tag>   # a stable tag and its nightly share a commit
   ```

   Every later step works from `origin/main`, never local `main`. On the 3824 sync local `main` was stale behind PR #42, and the first merge started from it.

2. List what upstream changed in the files we changed. Read each of those commits before you merge.

   ```bash
   OLD=v0.1.12-nightly.20261124.5191   # the "Last synced" tag above
   NEW=<new tag>
   git log --oneline $OLD..$NEW -- $(git diff --name-only $OLD origin/main)
   ```

3. Merge on a branch:

   ```bash
   git switch -c sync/upstream-<tag> origin/main
   git merge --no-ff $NEW
   ```

   Resolve each conflict so that upstream's new behavior and ours both survive. If upstream now does what one of our changes did, take upstream's version and delete ours.

   A file that merges with no conflict can still break the fork. On the 3824 sync, upstream #26238 dropped an argument the fork's code needed from a call in a file that git merged cleanly. So read the step 2 commits and run the seam tests even when every file merges clean.

4. Verify three things. Upstream owns testing upstream, so do not re-test upstream features.
   - Our code: the fork's tests, with the commands in [Seams to re-check](#seams-to-re-check).
   - The seams: the tests in [Seams to re-check](#seams-to-re-check), and the content check that the merged tree is upstream plus our diff and nothing else. Compare `git diff $NEW <merge>` with `git diff $OLD origin/main`. The only differences should be the conflict resolutions you made.
   - The deployment: build a release (see [Build a release](#build-a-release)) and run the verify skill's "Release check" (`node .agents/skills/verify-t3code/scripts/release-check.mjs pre --release <dir> --run <run folder>`). Every instance prod enables must pass. See [Test live without touching prod](#test-live-without-touching-prod).
5. Open the PR against `main`. Set "Last synced" in this file to the new tag in the same PR.
6. Have a reviewer from the other model family verify it, then merge with `--merge`. If the merge commit carries a test that the next commit fixes, that is fine. `main`'s first-parent history stays green because the PR lands as a merge commit.
7. Stop. The cutover is a separate step that Lee runs or approves.

Bugbot does not cover a sync: it refused PR #4 at 42,105 lines. Codex does, and the merge gate requires its review of the PR's current head, so comment `@codex review` after each push. On the 3766 sync (PR #39) it caught a regression three verifier rounds had missed.

## Build a release

`~/lim-v2/bin/t3-v2-deploy <ref>` builds `<ref>` from the main checkout `~/lim-v2/code/t3code-v2` into the same linux-x64 `t3` archive upstream ships. It names the release `t3-<tag>-lim.<sha>-linux-x64` after the nightly that `git describe --tags --match 'v*-nightly.*'` finds, or after the stable tag on that nightly's commit, so run `git fetch upstream --tags` in that checkout first. It unpacks the release into `~/lim-v2/service/t3code/prod/releases/` and smoke-tests it on port 13995.

Since upstream #26912 the Linux archive carries `lib/libatomic.so.1` and sets `t3`'s RUNPATH to it with `patchelf`, so the build host needs the `patchelf` and `libatomic1` packages. Without `patchelf`, `build-cli-archive.ts` stops with `spawn patchelf ENOENT`. This machine got `patchelf` during the `v0.1.5` sync.

The script never switches prod. It ends by printing the `t3-v2-cutover` command for the new release, with its sha256.

## Cut over

Lee runs or approves every cutover. Pass the seam tests, the feature drives in `.agents/merge-brief.md`, and `release-check.mjs pre` in order first, and link the `pre` report in the cutover ask.

1. Run `~/lim-v2/bin/t3-v2-cutover <release-name> <sha256-of-t3>`. The restart ends every T3 thread on prod, including the one that starts it. So run it from a terminal, or from a T3 thread as a detached `systemd-run --user` job.
2. The script never waits for prod to go idle, because it may never be idle. It lists the runs the restart interrupts, which T3 resumes after the update, and goes ahead. It backs up `statev2.sqlite` into `prod/data/backups/`, switches `prod/current`, restarts `t3code-v2-prod`, and checks that the new binary answers 200 on 13987. If the check fails, it switches back once.
3. After the switch, whether the check passed or failed, it starts `t3-v2-triage`, a headless Claude Code agent outside T3. The agent writes `report.md` in `~/lim-v2/notes/t3-v2-cutover/<time>-<release>/`.
4. Read the report. Reload every open T3 browser tab. A tab keeps the web client it loaded before the restart, and an old client can reject values the new server sends. The report ends with that reminder.
5. Keep the backup. A release can rewrite data on first start. 3238 compacted 54,269 events, so its backup is the only uncompacted copy.

To roll back, run `t3-v2-cutover <previous release>`, and never point `prod/current` at it by hand. `facts.env` in the run folder names the previous release. A rollback runs the old binary on data the new one may have migrated or compacted. Nobody has tested that for 3238.

## Fixes owed upstream

Two are open. The first is the Cursor worker registration above. Upstream `main` still refuses a provider the process launcher spawned (checked at `v0.1.12-nightly.20261124.5191` and `main` on 2026-11-24). The second is the window of a custom `[1m]` Claude model. Upstream's `claudeContextWindow` looks the reported window up under the suffixed id, and Claude Code reports it under the bare id, so upstream's context meter shows no window for that model. The fork's fix is the bare-id lookup in Thread settings above (checked at upstream `main` `924d9c1fff` on 2026-11-24).

No others are open. Worktree isolation for delegated tasks (pingdotgg/t3code#19102) was raised during the 3238 sync. It is merged upstream and shipped in 3238, so the fork owes nothing there. pstack-lim could use it in place of the `git worktree add` steps its skills ask helpers to run, which is a change for that repository.

Two gaps could go upstream. The first is the pair of Personal Team fixes in `apps/mobile/app.config.ts`: upstream's `T3CODE_IOS_PERSONAL_TEAM=1` path still writes `aps-environment` into the entitlements, because its strip plugin is registered last and so runs first, and still pins `appleTeamId` to T3's team, which a Personal Team cannot sign for.

The second is in the web client. It warns when the server is older than the client (`apps/web/src/versionSkew.ts`), but not when the client is older than the server, so a tab left open across a server update keeps an old client until it happens to reload. The fork covers it with the reload line in the cutover report.
