## What the fork adds

Everything else is upstream. `git diff --stat v0.1.10-nightly.20261112.4606 main` lists every file that differs, and that list should match this section.

- **Restart-held queues resume** (in `apps/server/src/fork/HeldQueueResumer.ts`, with its tests in `apps/server/src/fork/HeldQueueResumer.test.ts`). Upstream holds every queued message at a restart and waits for **Resume**, by design (upstream `6c9d827a41`, "require explicit consent before draining them"). This fork resumes a queue that only a restart held, once the thread is quiet again and its last turn ended well, when **Continue threads after restarts** is on for the project. A queue held by **Stop**, a provider failure, a missing worktree or a disabled instance stays held, and so does one whose last turn was cut, stopped or failed, whose thread waits on an answer or a secret, that the user stopped after the restart held it, or whose hold is older than the outbox's seven-day retention. A queue whose next run's provider stopped on a usage limit with a reported reset still ahead stays held until that reset, then resumes, the same as core's own automatic start. Upstream also releases every held queue when the user sends a message from web or mobile (upstream `62d98096ca`, #21473), and the two never start a queue twice: a send writes `queueHeld: false` under its own command id, which the resumer reads as a release, and a resume that lands after a send only rewrites a flag that is already off. It reads a bounded tail of the thread's event stream on the server's read-only connection. It reads the hold's cause from the stored command id of the event that set `queueHeld`, because the flag has no reason field. The upstream files we changed are `apps/server/src/server.ts` (one registration line), the keep rule in `apps/server/src/orchestration-v2/ProjectionMaintenance.ts`, `docs/user/composer.md` and `docs/user/updating.md`.
- **The fork's mobile identity** (PR #31). `APP_VARIANT=lim` in `apps/mobile/app.config.ts` is a fourth variant, **T3 Code Lim**, with the bundle id `ai.liminal.t3code.lim.mobile`, the scheme `t3code-lim` and the nightly icon. It has no relying party, which turns off everything that assumes T3's cloud: Clerk, the relay, the `clerk.t3.codes` associated domains, the `app.t3.codes` thread links (upstream #29815) and EAS updates. `vp run ios:lim` in `apps/mobile` builds it for a USB-connected phone under a free Apple ID, and `docs/operations/mobile-lim-ios.md` is the runbook. Two upstream Personal Team fixes ride along: the strip plugin is registered first so it runs after expo-notifications adds `aps-environment`, and a Personal Team build no longer pins T3's Apple team id (it takes `T3CODE_APPLE_TEAM_ID` or lets Xcode ask). The upstream files we changed are `apps/mobile/app.config.ts` and `apps/mobile/package.json`.
- **Delegated requests time out** (in `apps/server/src/fork/DelegatedRequestTimeout.ts`, with its tests in `apps/server/src/fork/DelegatedRequestTimeout.test.ts`). A delegated child can wait forever on a permission prompt or a question that no human will answer. A child in Supervised mode (`approval-required`) asks before each write, and no agent can approve it. Claude Code blocks an `rm` whose path is built from a loop variable outright, even under bypass permissions, so that command fails rather than waits. Upstream wakes the parent only for a child's question, and nothing upstream times a request out. This fork wakes the parent at once when an app-owned child raises an approval. The wake's notification has outcome `unknown`, because upstream drops a `delegated_task` wake with outcome `updated` that matches no pending child question. The message holds the prompt and the reason the provider gave, says an agent cannot approve it and the user can, and says when T3 will decline it. Upstream's own wake still covers questions. A request on a delegated child that is still pending ten minutes after it was raised gets a note that no human is available. A Claude approval is declined with the note as its feedback, which the model reads as the tool's result, and the note quotes Claude's reason, which often names the fix (a literal path). A Codex approval is declined with Codex's own fixed text, because Codex takes no feedback. A question gets the note as the answer to each of its questions. The child then works around it, or stops and says in its final message what it needed. A top-level thread, a fork and a provider-native subagent are never touched. The deadline is the request's `createdAt`. A sweep at start and every minute re-arms it, so after a restart a question that recovery kept is still answered, and the answer becomes the child's next message. A pending approval does not survive a restart, because recovery expires it. A child that a linked environment launched here through `delegate_task` carries `delegatedFrom` on its thread, so it gets the deadline too, with no parent here to wake. The parent's own server cannot see that request (`readRemoteTask` reports no question or approval), so only the server that runs the child can answer it. `T3CODE_DELEGATED_REQUEST_TIMEOUT=off` in the server's environment turns the module off. The verify skill's `features/delegated-requests.md` drives it. The upstream files we changed are `apps/server/src/server.ts` (one registration line) and `docs/user/thread-sidebar.md`.
- **A project's agents get its own TMPDIR** (in `apps/server/src/fork/ProjectTmpDir.ts`, with its tests in `apps/server/src/fork/ProjectTmpDir.test.ts`). Agents kept writing scratch files to the shared `/tmp` whatever their instructions said. Every agent T3 launches on this machine now gets `TMPDIR` set to `<workspace root>/.pstack/tmp/`, one per project and shared by all its threads, worktree threads included, so `mktemp` and most tools write beside the project's run folders. `RuntimePolicyV2` resolves it for each turn as `projectTmpDir` on the runtime policy, and each adapter sets it on the process it spawns with `withProjectTmpDir` from `packages/provider-core/src/server/instanceEnvironment.ts`. Codex is the exception. T3 runs one Codex app-server per instance and shares it across projects, so `codexThreadRuntimeParams` in `CodexAdapterV2.ts` puts `shell_environment_policy.set.TMPDIR` in each thread's `config` on `thread/start`, `thread/resume` and `thread/fork`, and Codex merges that key into the user's own policy. Codex ignores `config` when it resumes a thread that is already loaded, so a rollback that resumes an unloaded thread passes that thread's own policy (`runtimePolicy` on the rollback input, from `CheckpointRollbackService.ts`) rather than the session's. The ACP adapter also gives its client terminals the directory, so Devin's commands get it. `ProjectTmpDir` makes the folder and chmods it owner-only on every launch, so a folder made earlier at 0755 is tightened too, and adds `.pstack/` to the repository's `.git/info/exclude` once per root when no ignore rule covers it yet, never to a tracked `.gitignore`. An instance whose environment variables set `TMPDIR` keeps its own. A thread with no project, or a missing or unwritable root, gets no override, and the server logs why once per root. Claude, Codex, Grok, OpenCode v1, Pi, Muse and the ACP adapter's FX and ACP registry get it. Cursor does not: `@cursor/sdk` 1.0.38 (and 1.2.0) runs a local agent's shell inside the server's own process with no per-agent environment. Antigravity keeps its per-process `TMPDIR`, which holds its 1 GB unpack and is removed on exit, and OpenCode v2 runs one server per instance for every project. Claude Code keeps foreground task output under its `TMPDIR`. Upstream's live output tail in `ClaudeTaskOutputTail.ts` follows that since #24176, so the adapter hands it the same project `TMPDIR` it gives Claude. The upstream files we changed are `packages/provider-core/src/server/ProviderAdapter.ts` (the `projectTmpDir` field), `instanceEnvironment.ts` beside it, `apps/server/src/orchestration-v2/RuntimePolicy.ts`, `runtimeLayer.ts`, `Adapters/ClaudeAdapterV2.ts` and `Adapters/CodexAdapterV2.ts` in `orchestration-v2/`, `CheckpointRollbackService.ts` beside them, `packages/provider-acp/src/server/adapter.ts`, `adapter.ts` in `packages/provider-grok/src/server/`, `provider-opencode`, `provider-pi` and `provider-muse`, and `docs/user/install.md`. The upstream tests we changed are `RuntimePolicy.test.ts`, `CheckpointRollbackService.test.ts`, `ClaudeAdapterV2.test.ts`, `CodexAdapterV2.test.ts`, `AcpAdapterV2.test.ts` and `GrokAdapterV2.test.ts` in `orchestration-v2/`, and `packages/provider-core/src/server/instanceEnvironment.test.ts`.
- **Claude threads on Limbase** (in `apps/server/src/fork/Limbase.ts`, with its tests in `apps/server/src/fork/Limbase.test.ts`). A Claude instance whose **Limbase home** is set runs its threads on Limbase, the memory service on this machine, so a thread can run for millions of tokens. Limbase captures every message, keeps the SDK's own compaction off, and when a thread passes 700,000 tokens it moves the session to a compacted view of about 100,000 tokens. The adapter's `ensureThread` creates one Limbase thread per provider-thread row through the home's socket, and stores its id as `nativeMetadata.limbaseThreadId`. A row that already has one keeps it, so upstream's fresh-session fallback continues the same Limbase thread. The adapter's one `query()` call takes the `query` that `Limbase.queryFor` returns, which runs the SDK through Limbase's Agent SDK host, aliased by the provider-thread row id. An install changes the CLI's session id and announces it in a second `init`. Upstream's `/clear` path (`clearedNativeSessions`) already stores that id as the row's resume id at each `provider_thread.updated`, while the adapter keeps the live process's state under the process's first id. `Limbase.liveNativeId` resolves a moved row back to that first id wherever the adapter compares the stored row with the live process: `startTurn` (through `Limbase.onLiveSession`, so the next turn keeps the live process), `mcpAppQuery`, `interruptTurn`, `hasPendingBackgroundWorkForThread`, `applyModelSelection`, `stopTask`, `awaitBackgroundTasks` and `stopSubagent`. ## Branches and merges

- `main` is the upstream tag we last synced plus the fork's commits. Every change reaches `main` through a PR.
- Work goes on a short-lived branch: `fix/...`, `feature/...`, `sync/upstream-<tag>`. T3 creates `t3/...` branches for its own worktrees. Leave branches that another thread owns alone.
- Merge every PR through the merge gate, with a merge commit: `~/.agents/skills/poteto-mode/scripts/merge-gate/merge-gate --repo liminal-ai/t3code-v2 --pr <n> --method merge`. The gate checks the PR's checks, review threads, the independent review, the lead's acceptance and Lee's approval of any instruction-file text, then merges. Never merge a PR with `gh` yourself, never squash and never rebase `main`. A squash flattens upstream's history, so the next sync conflicts on every file upstream touched since. GitHub still allows squash and rebase on this repository, so nothing stops a wrong merge button but this rule.
- The fork's `origin` carries one old nightly tag, `v0.0.46-nightly.20261011.2980`. Upstream's tags come from `git fetch upstream --tags`. Without them, `git describe` names a build of today's `main` after that old tag.
- `gh` resolves this repository to `liminal-ai/t3code-v2` through `remote.origin.gh-resolved` in the shared git config. Without that line, `gh` picks the `upstream` remote and a bare `gh pr create` opens the PR on `pingdotgg/t3code`. If `gh repo view --json nameWithOwner` ever prints `pingdotgg/t3code`, run `gh repo set-default liminal-ai/t3code-v2`.

## Sync from upstream

1. Fetch the tag Lee picks, nightly or stable. Upstream cuts each stable tag on the same commit as a nightly (`v0.1.5` is `v0.1.5-nightly.20261029.3877`). `t3-v2-deploy` finds the nightly with `git describe --match 'v*-nightly.*'` and names the build after the stable tag on its commit when there is one, so a `v0.1.5` merge builds as `t3-0.1.5-lim.<sha>` and a `v0.1.7-nightly.20261101.4016` merge builds as `t3-0.1.7-nightly.20261101.4016-lim.<sha>`.

   ```bash
   git fetch origin
   git fetch upstream --tags
   git tag -l 'v*' --sort=-creatordate | head -10
   git tag --points-at <tag>   # a stable tag and its nightly share a commit
   ```

   Every later step works from `origin/main`, never local `main`. On the 3824 sync local `main` was stale behind PR #42, and the first merge started from it.

2. List what upstream changed in the files we changed. Read each of those commits before you merge.

   ```bash
   OLD=v0.1.10-nightly.20261112.4606   # the "Last synced" tag above
   NEW=<new tag>
   git log --oneline $OLD..$NEW -- $(git diff --name-only $OLD origin/main)
   ```

3. Merge on a branch:

   ```bash
   git switch -c sync/upstream-<tag> origin/main
   git merge --no-ff $NEW
   ```

   Resolve each conflict so that upstream's new behavior and ours both survive. If upstream now does what one of our changes did, take upstream's version and delete ours.

   A file that merges with no conflict can still break the fork. On the 3824 sync, upstream #26238 dropped an argument the fork's code needed from a call in a file that git merged cleanly. So read the step 2 commits and run the seam tests even when every file merges clean.

4. Verify three things. Upstream owns testing upstream, so do not re-test upstream features.
   - Our code: the fork's tests, with the commands in [Seams to re-check](#seams-to-re-check).
   - The seams: the tests in [Seams to re-check](#seams-to-re-check), and the content check that the merged tree is upstream plus our diff and nothing else. Compare `git diff $NEW <merge>` with `git diff $OLD origin/main`. The only differences should be the conflict resolutions you made.
   - The deployment: build a release (see [Build a release](#build-a-release)) and run it as a throwaway T3, never against prod, with one real turn on Cursor, Claude and Codex. The verify skill's "Release check" has the commands. See [Test live without touching prod](#test-live-without-touching-prod).
5. Open the PR against `main`. Set "Last synced" in this file to the new tag in the same PR.
6. Have a reviewer from the other model family verify it, then merge with `--merge`. If the merge commit carries a test that the next commit fixes, that is fine. `main`'s first-parent history stays green because the PR lands as a merge commit.
7. Stop. The cutover is a separate step that Lee runs or approves.

Bugbot does not cover a sync: it refused PR #4 at 42,105 lines. Codex does, and the merge gate requires its review of the PR's current head, so comment `@codex review` after each push. On the 3766 sync (PR #39) it caught a regression three verifier rounds had missed.

## Build a release

`~/lim-v2/bin/t3-v2-deploy <ref>` builds `<ref>` from the main checkout `~/lim-v2/code/t3code-v2` into the same linux-x64 `t3` archive upstream ships. It names the release `t3-<tag>-lim.<sha>-linux-x64` after the nightly that `git describe --tags --match 'v*-nightly.*'` finds, or after the stable tag on that nightly's commit, so run `git fetch upstream --tags` in that checkout first. It unpacks the release into `~/lim-v2/service/t3code/prod/releases/` and smoke-tests it on port 13995.

Since upstream #26912 the Linux archive carries `lib/libatomic.so.1` and sets `t3`'s RUNPATH to it with `patchelf`, so the build host needs the `patchelf` and `libatomic1` packages. Without `patchelf`, `build-cli-archive.ts` stops with `spawn patchelf ENOENT`. This machine got `patchelf` during the `v0.1.5` sync.

The script never switches prod. It ends by printing the `t3-v2-cutover` command for the new release, with its sha256.

## Cut over

Lee runs or approves every cutover.

1. Run `~/lim-v2/bin/t3-v2-cutover <release-name> <sha256-of-t3>`. The restart ends every T3 thread on prod, including the one that starts it. So run it from a terminal, or from a T3 thread as a detached `systemd-run --user` job.
2. The script never waits for prod to go idle, because it may never be idle. It lists the runs the restart interrupts, which T3 resumes after the update, and goes ahead. It backs up `statev2.sqlite` into `prod/data/backups/`, switches `prod/current`, restarts `t3code-v2-prod`, and checks that the new binary answers 200 on 13987. If the check fails, it switches back once.
3. After the switch, whether the check passed or failed, it starts `t3-v2-triage`, a headless Claude Code agent outside T3. The agent writes `report.md` in `~/lim-v2/notes/t3-v2-cutover/<time>-<release>/`.
4. Read the report. Reload every open T3 browser tab. A tab keeps the web client it loaded before the restart, and an old client can reject values the new server sends. The report ends with that reminder.
5. Keep the backup. A release can rewrite data on first start. 3238 compacted 54,269 events, so its backup is the only uncompacted copy.

To roll back, run `t3-v2-cutover <previous release>`, and never point `prod/current` at it by hand. `facts.env` in the run folder names the previous release. A rollback runs the old binary on data the new one may have migrated or compacted. Nobody has tested that for 3238.

## Fixes owed upstream

None are open. Worktree isolation for delegated tasks (pingdotgg/t3code#19102) was raised during the 3238 sync. It is merged upstream and shipped in 3238, so the fork owes nothing there. pstack-lim could use it in place of the `git worktree add` steps its skills ask helpers to run, which is a change for that repository.

Two gaps could go upstream. The first is the pair of Personal Team fixes in `apps/mobile/app.config.ts`: upstream's `T3CODE_IOS_PERSONAL_TEAM=1` path still writes `aps-environment` into the entitlements, because its strip plugin is registered last and so runs first, and still pins `appleTeamId` to T3's team, which a Personal Team cannot sign for.

The second is in the web client. It warns when the server is older than the client (`apps/web/src/versionSkew.ts`), but not when the client is older than the server, so a tab left open across a server update keeps an old client until it happens to reload. The fork covers it with the reload line in the cutover report.
